## Design Specificity Verdict

**LLM assessment.** The mechanics are unmistakably authored for a homelab file manager: folders sort before files regardless of column, natural-order collation so `clip-2` precedes `clip-10`, F5/F6 wired the way Commander muscle memory expects, durable server-side transfer jobs that survive closing the tab, free space recorded per job, read-only enforced at the API and mirrored in four places in the UI, a 25-file threshold that stops a dropped `node_modules` before it commits you to a four-hour queue. Nobody reaches those decisions from a dashboard template.

The surface is a different story. Radial blue gradients at 15%/85%, `backdrop-filter: blur(22px) saturate(1.2)` on every panel, 14px radii, indigo accent, Lucide icons at 14–16px, 11–13px muted metadata. Swap the file rows for invoices and the composition would not object. Worse, the skin fights the scene: a NAS file manager is read at arm's length on a second monitor while something else has your attention, and this one puts the consequential information — which pane is active, which volume you are about to delete from, whether the copy finished — in 11–12px muted text and a 1px accent ring, while the loudest object on screen is a filled blue **Upload** button in *both* pane headers.

**Verdict: the interaction model is genuinely domain-authored; the visual language is generic and, at the moments that matter, aimed at the wrong thing.**

**Deterministic scan.** `detect.mjs --json frontend/src` exited 2 with **1 finding**: `layout-transition` at `frontend/src/index.css:1877` — `transition: width` on the upload progress bar. A true positive but low value; the animated element is a 5px bar inside a fixed-height row, so layout thrash is negligible. The detector found nothing else, which matches the design review's read that the problems here are compositional and behavioural rather than mechanical.

## Overall Impression

This is a product whose engineering is well ahead of its interface. The safety model — staged writes, verified copies, read-only by default, mount-boundary-safe deletion — is better than anything else in this category, and the dual-pane interaction is the real differentiator. But the interface systematically under-communicates: it hides outcomes in a panel that is closed by default, marks the active pane with a 1px ring, names files but never disks in destructive dialogs, and greys out five of seven centre controls without ever saying why.

The single biggest opportunity: **make the app tell you what just happened.** Nearly half the score lost sits in heuristics 1 and 9, and both resolve to the same missing component — a status region that lives outside the Inspector.

## What's Working

1. **Read-only is a first-class concept, not a flag.** `· RO` in the sidebar, `· read-only` in the breadcrumb, Upload/Folder/New-folder disabled with explanatory titles, move blocked when either side is read-only, enforced again server-side. For someone who mounts a backup array they cannot afford to write to, this obsessiveness is exactly right, and it is threaded through rather than bolted on.

2. **The delete confirmation is properly engineered.** `role="alertdialog"`, `aria-labelledby`/`aria-describedby`, initial focus on Cancel, up to four names listed with "and N more…", a separate recursive-folder warning, and a button that says "Delete permanently" rather than "OK". It works because it makes irreversibility the headline instead of the count.

3. **Transfers are durable server-side jobs.** Skip / Replace / Rename / apply-to-all, cancellation, per-job bytes and files and speed, an SSE stream with a REST snapshot on reconnect and a 30s poll fallback. Closing the tab does not kill a 400 GB move. This is the most homelab-correct decision in the codebase.

## Priority Issues

### [P0] Every error and every completion is rendered inside the Inspector, which is closed by default below 1440px

**What:** `copyError`, the editor-open failure, the text-preview failure and the whole `TransferPanel` are children of the `.inspector` aside. Below 1440px the Inspector defaults closed. Clicking the Edit pencil on a non-UTF-8 file issues a request that returns 500 and produces **no visible change whatsoever** — the reviewing agent reproduced it six times before checking the network log.

**Why it matters:** a dead click is the most corrosive interaction a tool can have. The user cannot tell whether the app is broken, the file is broken, or they mis-clicked, and their next move is to click again. Meanwhile a completed 400 GB copy reports itself in 11px grey inside a panel they may never open — the peak-end rule violated exactly at the end.

**Fix:** add a global status region anchored above the two panes, `role="status"` for progress and completion and `role="alert"` for failures, independent of the Inspector, dismissible, auto-clearing successes after ~6s. Keep the Transfers list in the Inspector as history. No user-initiated action may resolve into zero pixel change.

**Suggested command:** `$impeccable harden`

### [P1] Two CSS custom properties are self-referential, so the default theme has no destructive colour and no dialog elevation

**What:** `index.css:33` and `:213` read `--shadow-strong: var(--shadow-strong)`, and `:38` and `:218` read `--danger-text: var(--danger-text)`. Both sit in the dark token blocks — the default theme. They resolve to nothing, so every `box-shadow: … var(--shadow-strong)` is invalid and `--danger-text` inherits ordinary body white. The context menu's "Delete permanently", the delete dialog's warning icon and `.editor-error` all render in plain white; the delete dialog, context menu and editor window float with no elevation. Light theme is unaffected, which is why it went unnoticed.

**Why it matters:** the one colour signal reserved for irreversible actions is absent in the theme almost everyone uses. Introduced by a blanket find-and-replace during the theme tokenisation pass that rewrote the token *definitions* along with their usages.

**Fix:** restore the literals — `--shadow-strong: rgba(0,0,0,0.65)` and `--danger-text: #fca5a5` in the dark blocks — and add a build-time or CI check that no custom property resolves to itself.

**Suggested command:** `$impeccable polish`

### [P1] Arrow keys and Select-all walk the unsorted array while the table renders the sorted one

**What:** `App.tsx:2146–2154` indexes `pane.entries`, the raw load-order array, while the table renders the `useMemo` sorted by `state.sortKey`/`sortDir`. Sort by Size descending and the arrow keys walk name order — the highlight jumps around the screen. `Cmd/Ctrl+A` has the same bug at `:2097`, selecting a different 500 items than the ones displayed. The moved row is never `scrollIntoView`'d, so under virtualization you can select rows you cannot see.

**Why it matters:** in an app whose next action may be "delete permanently", a keyboard selection that does not match the visible list is a data-loss path, not an annoyance. Introduced with the sortable-columns feature: the pane's render consumers were routed through the sorted array, the App-level keyboard handler was not.

**Fix:** derive one sorted array and pass it to both the pane render and the keyboard handler, and call `scrollIntoView({ block: 'nearest' })` on every arrow move.

**Suggested command:** `$impeccable harden`

### [P1] The stacked layout below 1280px is broken by CSS source order

**What:** `@media (max-width: 1279px) { .transfer-strip { flex-direction: row } }` sits at `index.css:341`, but the base `.transfer-strip { flex-direction: column }` sits at `:770` — later in the file, identical specificity, so the base wins. Measured at 1100px the strip is **278px tall** and nearly empty, wedged between the panes, pushing the destination pane below the fold and making the document rather than the panes scroll. At the same widths the Inspector's `left: 14px` and `right: 14px` combine into a full-bleed fixed overlay covering both panes, and `.side-panel` is capped at 200px, clipping the second volume.

**Why it matters:** below 1280px you can never see source and destination at once — which is the entire product.

**Fix:** move the responsive block after the base rule or scope it with a class; give the stacked strip a 48px horizontal bar with labeled Copy/Move buttons; cap the Inspector overlay at 360px with a scrim; turn the stacked sidebar into a horizontal volume switcher.

**Suggested command:** `$impeccable adapt`

### [P1] The centre strip is seven unlabeled 28px icons, and on a read-only destination Delete is the only live control

**What:** with files selected on a writable pane and a read-only volume opposite, Copy →, ← Copy, Move →, ← Move and Rename are all disabled and **Delete permanently is the sole enabled control** between the panes. No reason is shown for any of the disabled buttons, because a disabled button cannot surface the message the transfer handler would have given. `.icon-btn` has no `:disabled` styling at all — a disabled New-folder button computes `opacity: 1` and still takes its hover background.

**Why it matters:** the destructive action is left as the only affordance at exactly the moment the user is confused about why nothing else works. At 14px, chevrons versus double-arrows do not distinguish copy from move at a glance.

**Fix:** collapse the strip to two labeled buttons, **Copy →** and **Move →**, whose direction follows the active pane. Move Rename and Delete beside the "4 of 8 selected" count in the pane footer, where the selection they act on is visible. Replace silent disabling with an inline reason: "Backup 4TB is read-only". Add real `:disabled` styling.

**Suggested command:** `$impeccable clarify`

## Persona Red Flags

**Alex (impatient power user)** — pulling last night's footage from Media Server to Backup 4TB:
- No search, filter or type-ahead anywhere. In a `Footage/` folder with 800 clips his only tool is scrolling.
- Type-ahead is not merely missing, it is hijacked: pressing `g` or `l` unmodified flips the pane between grid and list. Typing the first letters of a filename scrambles his view.
- He sorts by Size to find the big files, arrows down, and the selection walks name order instead.
- He hits F5; the source tiles stay highlighted and the footer still reads "4 of 8 selected", so he cannot tell it fired. A second F5 silently queues a duplicate copy.
- The copy finishes and reports `completed` in 11px grey inside a closed panel.
- He right-clicks in the pane he has not clicked yet: Copy to…, Move to…, Rename and Delete are all greyed out, because the menu reads the stale active-pane props. Every first right-click in a pane is wasted.
- The Date modified column truncates to "26 Jul 2026, …" at 1100px — the time is what he sorted on, and it is the part cut.

**Sam (keyboard and screen reader):**
- **81 tab stops in a 17-item folder** — every row, every select button, every pencil carries `tabIndex={0}`. No roving tabindex, no skip link. In the 10,000-entry folder this app explicitly supports, Tab is unusable.
- **No `aria-live` region exists anywhere** — verified, zero matches in the source. Transfer completion, copy errors, the editor failure and the selection count are all silent.
- The Edit pencil is `opacity: 0` until hover or focus, and Enter never opens the editor, so Monaco is effectively mouse-only — contradicting `docs/KEYBOARD.md`.
- Every grid tile is a `div role="button"` containing a real `button`, sometimes two. Invalid nesting; each photo announces as an unnamed button.
- `aria-selected` is set on plain `<tr>` elements in a table with no `role="grid"`, so selection state is not exposed.
- Which pane is active is never programmatically exposed — no `aria-current`, no announcement, just a 1px ring. Sam cannot tell which side F5 copies *from*.
- The Rename dialog has no Escape handler and the global handler early-returns while it is open. Delete and New folder both handle Escape; Rename does not. None of the three modals traps or restores focus.
- No `h1` exists, and there are no `main`, `nav`, `header` or `footer` landmarks — the heading outline is `h2 "Media Server"`, `h2 "Backup 4TB"`, `h3 "Inspector"`.

## Minor Observations

- Opening a non-UTF-8 file in the editor returns **500** rather than 415: `writeFSError` handles neither `ErrInvalidText`, `ErrTooLarge` nor `ErrNotFile`, so they fall through to the internal-error default. `writeTransferError` maps them correctly, which is where the divergence comes from.
- Thumbnail requests are 429-rate-limited and retried up to four times with no placeholder or skeleton, so tiles show broken-image glyphs and then pop in one by one.
- The transfer meta line — `341 KB / 341 KB · — · 4/4 files · 29 TB free at start` — packs six values into one 11px run. "free at start" is engineer voice, and `[copy]` prefixing the job is log formatting leaking into UI.
- The grid selection checkbox sits directly on the photo with no scrim; on a light or busy image it disappears in both themes.
- The context menu's "Copy to Media Server" names the volume, so with both panes on one volume it offers to copy to the place you are already standing. It should name the destination folder.
- `index.css` carries ~60 lines of duplicated light-theme token blocks (the `prefers-color-scheme` copy and the `[data-theme='light']` copy), which is the structural reason a token can go missing from one and not the other.
- Sort header buttons are 16px tall (`Name` 164×16, `Date modified` 112×16, `Size` 64×16); 20+ controls sit between 26 and 32px, all under the 44px touch guideline. Acceptable for a desktop-first tool, disqualifying for touch.
- Login copy — "Sign in to browse configured storage volumes" — is passive and system-centred for a product whose pitch is "your homelab".
- No console errors or warnings were observed across login, navigation, theme switch and resize.

## Questions to Consider

1. The real job is "get 400 GB off the failing disk before tonight". There is no search, no filter, no type-ahead, and the job queue lives inside a collapsible panel — while the loudest pixel in each pane is an **Upload** button. What is this interface optimised for, and what would it look like optimised for *finding and moving* instead?
2. Both panes can show the same volume and the same folder, and the delete dialog names the file but not the disk. What changes if pane identity becomes the **folder** rather than the volume — and could any dialog still lie by omission?
3. This interface disables controls where it could explain them. What if nothing were ever silently greyed out — if every unavailable action stated its reason at the point of refusal — and how much of the Inspector's error plumbing would then become unnecessary?
